# 同游现场（Museum Live Room）

## Why

`together.html` 需要发起者先确定馆、日期、时段，再把链接分发给特定的几个家庭。它解决"和谁一起"，但对**在馆那一刻**没有任何帮助：一个家长站在展厅里，既不知道今天有没有别的家庭也在，也没有任何低成本的交互方式。

`museum-live.html`（同游现场）补的是这一段。它把粒度从"本场活动"放宽到"这座馆"：一个博物馆一个房间，内容只有打卡广播和预设语句。

## Flow

1. 从 `museum-live.html?museum=<id>` 进入某座馆的现场。没有参数时先给一个选馆页。
2. 房间头部显示两个粗粒度数字：**近 90 分钟在馆家庭数**和**今天来过家庭数**。只按时间窗统计，不显示谁在线，不显示实时位置。
3. 动态流由两类记录组成，按时间正序排列：
   - **打卡广播**：由真实打卡行为生成。进入打卡页写一条"到馆"；每完成一项任务写一条进度；全部完成写一条"集齐"。
   - **预设语句**：家长从 12 句预设中选一句发出（见下方分组）。
4. 底部是语句选择器。槽位句（展品、「我们已完成 N 项任务」）需要先补全槽位才可发送。
5. 家庭代号默认为设备短号派生（`家庭 a3f9`），可在"改一下别人看到的代号"里修改，上限 12 字。
6. 房间内容 12 小时后自动过期，双方都不需要清理。

### 语句目录

| 分组 | 语句 |
|---|---|
| 招呼 | 我们到了 / 今天馆里人多吗？ / 有人也在馆里吗？ |
| 展品 | 这件太值得看了 / 一起看这个？ / 我们刚看了「{展品}」 |
| 行程 | 我们在排队 / 稍等 10 分钟 / 我们往下一个展厅了 |
| 成就 | 我们已完成 {n} 项任务 / 干得漂亮 / 谁集齐了全部任务？ |

槽位数据不全时，对应该句直接不显示（例如本机没有已完成任务，就不显示成就槽位句）。

## 入口

| 入口 | 位置 | 链接 |
|---|---|---|
| 打卡页横幅 | `museum-checkin.html` 馆名下方 | `museum-live.html?museum=<当前馆 id>` |
| 同行探索页顶栏 | `together.html` 顶栏 | `museum-live.html`（无参数，进选馆页） |

打卡页横幅由 `updateLiveRoomLink()` 在 `currentMuseum` 解析完成后填充：只有拿到真实馆 id 才显示，**访客自建馆（personal museum）不显示**——房间键仅对官方馆注册的 id 有意义——避免出现死链。

> 试点范围：当前横幅对**所有官方馆**显示（`MUSEUMS_META` 里 122 座，含南京博物院 `nanjing-museum`、上海博物馆 `shanghai-museum`）。选馆页同样列出全部馆，二者保持一致。若后续要收紧为小范围灰度，只需在 `updateLiveRoomLink()` 里加一个白名单判断，不必改数据层。

## 安全与隐私

这一层的核心性质是：**房间记录里不存任何自由文本。**

- 一条 `message` 只存 `phraseId` + 数字槽位；一条 `broadcast` 只存 `event` + 数字。
- 渲染时由**读取方**用自己的语句目录还原文案，槽位数字做范围校验；越界索引直接丢弃。
- 因此即使有人绕过页面直接往 KV 写垃圾，也到不了任何人的屏幕上——他最多能组合出目录里已有的句子。这让我们在没有审核能力的哑存储上也能安全承载一个公共房间。
- 未加载到馆藏时，展品槽位退化为泛称（"一件展品"）而不是隐藏整条消息，避免把别人的网络问题当成内容问题。
- 在场统计只数能通过校验的记录，避免灌垃圾刷高"在场人数"。
- 本地限速：20 秒冷却 + 每小时 12 条上限。

其他边界：

- 不能自由输入，不能 @ 某人，没有回复线程，没有点赞、排名、公开成员列表。
- 不收集姓名、联系方式、孩子照片、实时位置。代号是设备短号派生，不是身份。
- 房间记录 12 小时后过期。

## 实现

| 文件 | 作用 |
|---|---|
| `museum-live.html` | 页面骨架 |
| `css/museum-live.css` | 样式 |
| `js/museum-live.js` | 渲染与交互（20 秒轮询，页面不可见时不轮询） |
| `js/live-room-service.js` | 数据层：房间键、读写、目录、校验、在场统计 |
| `js/museum-checkin.js` | `broadcastRoom()` 把打卡行为镜像进房间；`updateLiveRoomLink()` 渲染打卡页入口横幅 |

- **房间键**：`museumcheck-live-<museumId>`，按馆分片，避免一个键装下所有博物馆。
- **写入**：`POST {key, sortKey: "<timestamp>-<random>", value, expireAt}`，TTL 12 小时。
- **读取**：`GET ?key=...&sortKey=*`，客户端过滤。房间键很轻（空键 15 字节），所以轮询成本可控。
- **不要用全局信号键做这件事**：`museumcheck-visit-signals` 实测 1.6 MB / 8.9 s，`museumcheck-events` 1.0 MB / 3.7 s，两者都不能轮询。
- **同设备识别**：与本页共用 `museumcheckVisitVisitorId`，所以"你们"在打卡页和现场页是同一个身份。
- 馆藏名单走 `MuseumDataLoader`（缓存读），仅用于展品槽位。

`?demo=1` 会附加一组本机示例数据，只用于设计评审，不会上传。

## Validation

这是一个可逆的实验，验证顺序有意从最小开始：

1. **先看在场和广播有没有人用**——房间打开率、停留、以及打开后是否进入打卡页。如果连"今天有 3 组家庭在馆"都没人看，加语句也救不活。
2. **再看语句有没有人发**——发出条数 / 房间打开数。这一步才验证"受限语句"是否够用。
3. 结构化的边界保持不变；只有当 1、2 都为正时，才考虑把 `together` 的本场活动层接进来做第二级（小群）。

不做的事：不在有数据之前扩大自由表达范围，不因为"看起来不够热闹"就放开输入框。
